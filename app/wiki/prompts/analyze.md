# 第一步：编译分析

你在为这个知识库编译新素材。**这一步只做规划，一个字正文都不要写。**

读完源文档，对照现有页面清单，决定这次要产出哪些页面、每个页面做什么操作。

## 输出

只输出一个 JSON 对象，不要任何解释文字、不要代码围栏。

```json
{
  "pages": [
    {
      "slug": "意图路由",
      "type": "concept",
      "op": "create",
      "title": "意图路由",
      "summary": "用规则显式分流用户意图，绕开向量检索不可靠的问题",
      "sources": ["我的简历.md"]
    }
  ],
  "contradictions": [
    {
      "a": "A 处原文摘录（含出处）",
      "b": "B 处原文摘录（含出处）",
      "why": "为什么这两处无法同时成立"
    }
  ],
  "gaps": ["素材里没有覆盖、但读者大概率会问的主题"]
}
```

字段说明：

- `slug`：文件名（不含 `.md`），中文，遵循 SCHEMA.md 第五节的命名规范
- `type`：`summary` / `entity` / `concept` / `comparison` / `overview` 之一
- `op`：`create` / `update` / `skip`
- `title`：页面显示名
- `summary`：**一句话**，会被抄进 index.md
- `sources`：来源文件名列表

## op 怎么定（最重要）

- 目标页**不存在** → `create`
- 目标页**已存在**，且本次来源包含该页**还没有的事实** → `update`
- 目标页**已存在**，且本次来源没有带来新东西 → `skip`

**反 churn：同义改写、调整措辞、重新排版、把两句话合成一句，都不算「新的事实」。**

模型天然倾向于「既然读了就产出点什么」。对同一份文档的第二次编译，
正确的结果往往是**什么都不做**——所有页面都 `skip`。

## 页面要几个

这是最要紧的判断，也是**最容易做少**的地方。

- **摘要页**（`summaries/<源文件名>`）：一份文档一个，必然有。
- **实体页**（`entities/`）：源文档里**被命名的具体事物**——项目、系统、产品、组织、人物。
  有名字、且围绕它不止一句话，就该建一页。
- **概念页**（`concepts/`）：原文里有独立描述段的**方法、技术、流程、主题**。
  判断标准是「它在原文里有没有自己的段落/小节」。
- **总览页**（`overview.md`）：全局唯一一个，首次编译时建。

按这个标准，《我的简历》里「项目经历」下的每一个编号小节都是一个概念页，
项目本身是一个实体页，此外还会有若干实体与概念。
**一份上万字的文档，编译出 5–12 个页面是正常的；只列出 2–3 个，基本可以断定是漏了。**

## 页面之间怎么分工

细节得有地方放，摘要页才不会膨胀成原文的副本：

- **摘要页**回答「这份文档是什么、覆盖了哪些方面」——它是入口，不是全文。
- **实体页 / 概念页**回答「具体是怎么做的」——原文的数字、流程、取舍、结论都归这里。

如果你发现某个主题的内容多到摘要页装不下，那不是摘要页该写短一点，
而是**它本该有个自己的页面**。

## 但也不要注水

原文里只被提了一句、没有展开的名词（比如只出现在技能清单里的某个库名），
不要单独开页——那种在相关概念页的正文里顺带提一句就够了。

最终判断方法：**假设面试官问到它，删掉这页会不会让答案缺一块？**
会 → 建页。不会 → 不建。

## 矛盾

严格按 SCHEMA.md 第六节判定。特别提醒：**跨文档的技术栈差异、颗粒度差异、
通用描述与具体实例的差异，都不是矛盾，不要报。**

`contradictions` 里每一条都必须同时给出 A、B 两处原文摘录 + 不相容的理由。
凑不出两段真正打架的原文，就留空数组。
