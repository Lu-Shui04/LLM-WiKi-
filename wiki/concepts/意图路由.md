## 摘要

意图路由是速购 AI 客服系统里用 LangGraph StateGraph 实现的分流方案：最前面放意图识别节点，识别后通过条件边把请求分到订单 Agent、RAG 节点或通用对话，置信度不足统一走通用对话兜底，且通用对话里识别出明确诉求可再次分流回专用路径。

## 要点

- 原方案是单个 Agent 啥都管，用户问什么自己看着办，链路一长就难定位
- 用 LangGraph 搭 StateGraph，最前面是意图识别节点，识别完通过条件边分流
- 订单类走订单 Agent，政策知识类走 RAG 节点，剩下的走通用对话
- 意图置信度不够或落不进明确分类时统一走通用对话，不硬塞专用路径
- 通用对话里如果又识别出明确的订单/政策诉求，会再次分流回去
- 新增一类意图只要加一个节点和一条边，不动已有路径
- 结果：路径职责单一，该查接口的场景一定走订单 Agent，错分代价被压低
- 代价：意图识别成为新的单点，识别错会把请求带偏，所以这一层单独做了兜底

## 细节

### 来自《我的简历》

最早是单个 Agent 啥都管，用户问什么它自己看着办，要么查接口要么答知识。问题有两个：一是链路一长就难定位，一次回答不对，分不清是意图判断错了、订单接口返回有问题、还是知识库召回不准；二是把「查订单」和「答政策」混在一个 Agent 里，它有时该查接口的时候不查，直接凭印象编了个订单状态，这在客服场景是致命的。

改动是：用 LangGraph 搭了一个 StateGraph，最前面是意图识别节点，识别完通过条件边把请求分流。订单类走订单 Agent，政策知识类走 RAG 节点，剩下的走通用对话，最后由一个汇总节点把结果整理成自然语言回复。新增一类意图，只要加一个节点和一条边，不动已有路径。

结果：每条路径职责单一，出错能精确定位到是哪个节点；该查接口的场景一定走订单 Agent，不会再出现凭空编订单状态的情况。代价是意图识别成了新的单点，识别错会把请求带偏，所以这一层单独做了兜底。

在取舍意识里，项目作者也强调：意图路由让定位变容易，但意图识别成了新的单点，识别错会带偏请求，所以加了兜底——不确定时走通用对话，不硬塞专用路径。多 Agent 分流职责清晰，但带来状态同步成本，所以只在意图边界清楚的地方拆，没无限拆。

### 来自《常见问题回答》

架构上把订单类意图路由到专门的订单 Agent，这条路径就是为调工具设计的。意图识别错了会有兜底：意图置信度不够、或者落不进明确分类时统一走通用对话，由模型正常回答并在需要时引导用户补充信息或转人工，而不是硬塞专用路径。专用路径只在意图明确时进，错分代价被压低。另外通用对话里如果又识别出明确的订单/政策诉求，会再次分流回去。
