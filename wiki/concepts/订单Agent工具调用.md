## 摘要

订单 Agent 把订单查询能力做成 ReAct Agent + 工具调用，用 zod 定义参数、温度设 0，Prompt 和工具描述明确涉及具体订单信息必须通过工具获取。Agent 先想清楚调哪个工具、传什么参数，拿到真实接口结果再回复，这样订单类回答全部基于真实数据，幻觉直接消除。

## 要点

- 原方案是订单相关问题也让模型直接回答，没有实时数据只能编
- 架构上把订单类意图路由到专门的订单 Agent，这条路径就是为调工具设计的
- 定义订单查询、物流跟踪、用户订单列表几个 Tool，参数用 zod 定义 Schema
- 调模型时温度设成 0，保证生成的参数格式精确、不发挥
- Prompt 和工具描述里明确，涉及具体订单信息必须通过工具获取，不允许凭空回答
- Agent 按 Thought → Action → Observation 循环：先想清楚调哪个工具、传什么参数，拿到真实接口结果再组织回复
- 订单类回答全部基于真实数据，幻觉直接消除
- 中间步骤（调了哪个工具、传了什么参、返回了什么）暴露给前端展示，让用户看到 AI 在「查」而不是「猜」
- 代价：增加了链路依赖，接口慢或失败会拖累整体，所以做了失败处理和超时控制

## 细节

### 来自《我的简历》

早期订单相关问题也让模型直接回答。问题在于模型没有实时数据，只能编。用户问「我的订单 ORD-12345 到哪了」，它能一本正经地编一个物流状态出来，看着像那么回事，其实全错。

改动是把订单能力做成 ReAct Agent + 工具调用：定义了订单查询、物流跟踪、用户订单列表几个 Tool；每个工具的参数用 zod 定义 Schema；调模型时把温度设成 0，保证它生成的参数格式精确；Agent 按 Thought → Action → Observation 的循环，先想清楚要调哪个工具、传什么参数，拿到真实接口结果后再组织成自然语言回复。

结果：订单类回答全部基于真实数据，幻觉直接消除。作者把中间步骤（调了哪个工具、传了什么参、返回了什么）暴露出来推给前端展示，用户能看到 AI 在「查」而不是在「猜」，这个透明过程本身就提升了信任。

取舍上，工具调用消除了订单幻觉，但增加了链路依赖，接口慢或失败会拖累整体，所以对工具调用做了失败处理和超时控制。

### 来自《常见问题回答》

保证模型一定去调接口而不是自己编订单状态，靠两点：一是架构上把订单类意图路由到专门的订单 Agent，这条路径就是为调工具设计的；二是 Prompt 和工具描述里明确，涉及具体订单信息必须通过工具获取，不允许凭空回答。调模型时温度设 0，让它生成工具参数时格式稳定、不发挥。
