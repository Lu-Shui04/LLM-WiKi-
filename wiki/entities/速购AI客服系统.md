## 摘要

速购 AI 客服系统是面向电商场景的 AI 客服项目，把客服问题分成「查事实」和「问知识」两类，用 LangGraph 搭多 Agent 工作流，订单类问题必须调真实接口、政策类问题基于 RAG 检索知识库回答，搞不定时干净转人工，并通过 SSE 把 AI 处理过程可视化呈现给前端。

## 要点

- 技术栈：Vue3 / Node.js / Express / LangChain.js / LangGraph / RAG / pgvector / DeepSeek API / SSE
- 问题分两类：查订单、查物流等必须基于真实数据；退款政策、保修规则等答案在文档里
- 用 LangGraph StateGraph 做意图路由：订单走订单 Agent，政策知识走 RAG，其余走通用对话，最后由汇总节点整理回复；意图不确定时统一走通用对话兜底
- 订单 Agent 用 ReAct + 工具调用查真实接口，温度设 0，Prompt 和工具描述明确禁止凭空回答，消除订单幻觉
- RAG 按结构切分（chunkSize 500、overlap 50），Top-K 取 4，提示词禁止无依据编造，政策回答可追溯
- 退款等多轮流程进度存在图共享状态里，按会话隔离，记录流程进度、已确认信息和工具调用记录，不重复追问、不串用户
- 转人工触发条件：知识库查不到、意图识别多次落空、涉及高风险操作；转交时带用户问题、订单信息、对话历史
- 前端可观测性：后端通过 SSE 按事件类型推送节点切换、工具调用步骤、来源引用等，前端实时渲染处理轨迹
- 项目成果：订单回答 100% 基于真实数据、零幻觉；政策回答可追溯；多轮退款流程顺畅；高风险场景干净交接人工

## 细节

### 来自《我的简历》

项目背景是给电商做 AI 客服。客服问题分两类：一类是查事实，比如订单发了没、物流到哪了、商品支不支持七天无理由，必须查真实数据，编不得；另一类是问知识，比如退款政策、保修规则、优惠怎么叠加，答案在文档里，但客服人力扛不住高并发咨询。目标是做一个既能调真实接口查订单、又能基于知识库准确回答政策、搞不定时还能干净转人工的客服。

早期用单个 Agent 啥都管，暴露的问题是：链路一长就难定位，分不清是意图判断错了、订单接口返回有问题、还是知识库召回不准；把「查订单」和「答政策」混在一个 Agent 里，该查接口的时候不查，直接凭印象编了个订单状态，对客服场景致命。

后来拆成几个模块调整：

1. **意图路由 + 分支处理**：用 LangGraph 搭 StateGraph，最前面是意图识别节点，识别完通过条件边分流。订单类走订单 Agent，政策知识类走 RAG 节点，剩下的走通用对话，最后由汇总节点整理成自然语言回复。新增一类意图只加一个节点和一条边，不动已有路径。代价是意图识别成了新的单点，所以单独做了兜底。

2. **订单 Agent：必须调真实接口**：把订单能力做成 ReAct Agent + 工具调用，定义订单查询、物流跟踪、用户订单列表几个 Tool，参数用 zod 定义 Schema，模型温度设 0，按 Thought → Action → Observation 循环，先想清楚调哪个工具、传什么参数，拿到真实接口结果再组织回复。中间步骤暴露给前端展示，让用户看到 AI 在「查」而不是「猜」。

3. **RAG 筛选 + 防幻觉**：文档切分用 RecursiveCharacterTextSplitter，按内容结构切，chunkSize 500、overlap 50；检索控制 Top-K 取 4 条；Prompt 加硬性约束，只能基于检索到的内容回答，知识库里没有就明确说「这个我没有查到」并引导转人工。取舍是 Top-K 收紧会漏掉边缘信息，4 是反复试出来的平衡点。

4. **多轮状态**：在图共享状态里记录当前流程进度、已确认信息、工具调用记录。退款这种流程要先确认订单、再确认原因、再提交，不存进度会每轮重新问。用户补充信息时基于已有状态往下推进，退款等多轮流程能连贯走完。

5. **转人工**：设明确触发条件：知识库查不到、意图识别多次落空、涉及高风险操作。不再让模型硬答，而是带着已收集的上下文（用户问题、订单信息、对话历史）转给人工，人工不用从零开始问。

取舍意识上：意图路由让定位容易但引入单点，不确定时走通用对话；工具调用消除订单幻觉但增加链路依赖，所以做失败处理和超时控制；RAG 收紧 Top-K 降低噪声但会漏边缘信息；防幻觉指令让它敢承认不知道但也可能偏保守；多 Agent 分流职责清晰但带来状态同步成本，只在意图边界清楚的地方拆。

项目职责：独立负责 AI 客服系统全流程设计与开发，从需求梳理到架构落地；负责 LangGraph 工作流搭建、意图路由设计、订单 Agent 与 RAG 模块开发；负责前后端联调、SSE 流式推送与前端状态可视化。

项目成果：AI 处理大量高频标准问题，订单回答 100% 基于真实数据、零幻觉；政策回答可追溯、有来源引用，知识库外内容不再硬编；多轮退款流程体验顺畅，不重复追问；高风险场景干净交接人工，整体风险可控。

### 来自《常见问题回答》

本次 FAQ 补充了各模块在实践中的细节：

- 意图路由：意图置信度不够或落不进明确分类时统一走通用对话，不硬塞专用路径；通用对话里再次识别出明确订单/政策诉求会再次分流回去。
- 订单 Agent：架构上订单类意图路由到专门订单 Agent，路径为调工具设计；Prompt 和工具描述明确涉及具体订单信息必须通过工具获取，不允许凭空回答；温度设 0 让工具参数格式稳定。
- RAG：chunkSize 500、overlap 50 是政策类结构化文档试出来的，太大噪声多、太小政策被截断；Top-K 取 4 平衡召回与上下文干净度，均非默认值。
- 多轮状态：存在图共享状态里，按会话隔离，每个会话独立，不会跨用户串；记录流程进度、已确认信息和工具调用记录。
- 转人工：触发条件包括知识库查不到、意图多次落空、涉及金额纠纷/情绪激烈高风险场景；转交时携带用户问题、订单信息、对话历史。
- 前端可观测性：后端通过 SSE 按事件类型推送节点切换、工具调用步骤、来源引用、最终答案、完成、错误，前端按类型驱动状态更新，实时渲染「意图识别 → 查订单 → 整理回答」过程。
