#### 项目背景

这个项目是给电商做 AI 客服。客服问题分两类：

一类是「查事实」——我的订单发了没、物流到哪了、这商品支不支持七天无理由。这类必须查真实数据，编不得。

另一类是「问知识」——退款政策、保修规则、优惠怎么叠加。这类答案在文档里，但客服人力扛不住高并发咨询。

我们想做一个 AI 客服，既能调真实接口查订单，又能基于知识库准确回答政策，还要在搞不定时干净利落地转人工。

---

#### 一、从「单个 Agent 自由发挥」到「意图路由 + 分支处理」

**原方案：** 最早是一个 Agent 啥都管，用户问什么它自己看着办，要么查接口要么答知识。

**问题：**
- 链路一长就难定位，一次回答不对，分不清是意图判断错了、订单接口返回有问题、还是知识库召回不准
- 把「查订单」和「答政策」混在一个 Agent 里，它有时该查接口的时候不查，直接凭印象编了个订单状态，这在客服场景是致命的

**改动：**
我用 LangGraph 搭了一个 StateGraph，最前面是意图识别节点，识别完通过条件边把请求分流：
- 订单类走订单 Agent
- 政策知识类走 RAG 节点
- 剩下的走通用对话
- 最后由一个汇总节点把结果整理成自然语言回复

新增一类意图，只要加一个节点和一条边，不动已有路径。

**结果：**
- 每条路径职责单一，出错能精确定位到是哪个节点
- 该查接口的场景一定走订单 Agent，不会再出现凭空编订单状态的情况
- 代价是意图识别成了新的单点，识别错会把请求带偏，所以这一层单独做了兜底

---

#### 二、订单 Agent：从「凭印象答」到「必须调真实接口」

**原方案：** 早期订单相关问题也让模型直接回答。

**问题：** 模型没有实时数据，只能编。用户问「我的订单 ORD-12345 到哪了」，它能一本正经地编一个物流状态出来，看着像那么回事，其实全错。

**改动：**
把订单能力做成 ReAct Agent + 工具调用：
- 定义了订单查询、物流跟踪、用户订单列表几个 Tool
- 每个工具的参数用 zod 定义 Schema
- 调模型时把温度设成 0，保证它生成的参数格式精确
- Agent 按 Thought → Action → Observation 的循环，先想清楚要调哪个工具、传什么参数，拿到真实接口结果后再组织成自然语言回复

**结果：**
- 订单类回答全部基于真实数据，幻觉直接消除
- 我把中间步骤（调了哪个工具、传了什么参、返回了什么）暴露出来推给前端展示
- 用户能看到 AI 在「查」而不是在「猜」，这个透明过程本身就提升了信任

---

#### 三、RAG：从「召回即拼接」到「筛选 + 防幻觉」

**原方案：** 政策知识问答最早就是把召回的文档直接拼进上下文。

**问题：**
- 召回里混进弱相关段落，模型答政策就会前后矛盾
- 更糟的是知识库里根本没有的内容，它也会硬编一个看似合理的政策出来，等于在误导客户

**改动：**
- 文档切分用 RecursiveCharacterTextSplitter，按内容结构切（chunkSize 500、overlap 50），避免一条政策被截断
- 检索控制 Top-K（取 4 条），只把高相关的少量内容注入上下文
- Prompt 里加硬性约束——只能基于检索到的内容回答，知识库里没有就明确告诉用户「这个我没有查到」，并引导转人工

**结果：**
- 政策回答稳定且可追溯（能带来源引用）
- 最关键的是它学会了「承认不知道」，不再编政策
- 取舍是 Top-K 收紧会漏掉边缘信息，4 这个数是反复试出来的平衡点

---

#### 四、多轮状态：退款这种流程不能每轮都从头问

**原方案：** 早期每轮对话相对独立，没有把流程进度存下来。

**问题：** 像退款这种是多轮流程——要先确认订单、再确认原因、再走提交。如果不存进度，用户每说一句系统就像失忆一样重新问，体验极差，也容易在中途丢上下文。

**改动：**
在图的共享状态里记录：
- 当前流程进度
- 已经确认过的信息
- 工具调用记录

用户在多轮里补充信息时，系统基于已有状态往下推进，而不是从头来。

**结果：** 退款这类多轮流程能连贯走完，不重复追问。

---

#### 五、转人工：搞不定要干净地交接，而不是硬撑

**原方案：** 最初没有明确的转人工边界，模型遇到搞不定的也硬答。

**问题：**
- 客服场景里硬答比不答更危险——答错政策、答错操作会引发投诉
- 有些情绪化的、涉及金额纠纷的，本来就该人来处理

**改动：**
设了明确的转人工触发条件：
- 知识库查不到
- 意图识别多次落空
- 涉及高风险操作时

不再让模型硬答，而是带着已经收集到的上下文（用户问题、订单信息、对话历史）转给人工，让人工不用从零开始问。

**结果：** AI 处理掉了大量高频标准问题，复杂和高风险的干净交接给人，整体既提效又控住了风险。

---

#### 取舍意识

1. **意图路由** 让定位变容易，但意图识别成了新的单点，识别错会带偏请求，所以加了兜底——不确定时走通用对话，不硬塞专用路径
2. **工具调用** 消除了订单幻觉，但增加了链路依赖，接口慢或失败会拖累整体，所以对工具调用做了失败处理和超时控制
3. **RAG 收紧 Top-K** 降低噪声，但会漏边缘信息，4 是平衡出来的值
4. **防幻觉指令** 让它敢承认不知道，但也可能偏保守，把本来能答的也转人工了，所以兜底条件是反复调的
5. **多 Agent 分流** 职责清晰，但带来状态同步成本，所以只在意图边界清楚的地方拆，没无限拆

#### 一段可直接背诵的完整表达

这个项目是给电商做 AI 客服。客服问题分两类：一类是查订单、查物流这种必须基于真实数据、编不得的；一类是问退款政策、保修规则这种答案在文档里的。我们想做一个既能调真实接口查订单、又能基于知识库准确答政策、搞不定时还能干净转人工的客服。

早期我们用单个 Agent 啥都管，跑起来暴露了几个问题：链路长，出错分不清是意图错了还是接口错了；订单问题它没有实时数据就直接编一个状态出来；政策问答把召回结果直接拼进上下文，混入噪声就前后矛盾，知识库里没有的也硬编。

后来我做了几轮调整。第一，用 LangGraph 搭了带意图识别的状态图，订单走订单 Agent，政策走 RAG 节点，其余走通用对话，加新意图只加节点和边。第二，订单能力做成工具调用，用 zod 定义参数、温度设 0，Agent 拿到真实接口结果再回复，彻底消除订单幻觉。第三，RAG 按结构切分文档、只取 Top-4 高相关内容，并强制它没依据就如实说没查到。第四，退款这种多轮流程的进度存在共享状态里，不重复追问。第五，搞不定或高风险时带着已收集的上下文转人工。

改完之后，AI 扛掉了大量高频标准问题，订单回答全部基于真实数据，政策回答可追溯，复杂的干净交接给人。我最大的体会是，客服这种场景，让 AI「敢说不知道」「该查就查」比让它显得无所不能更重要，否则它编一个错的政策出来，比不答还糟。
